# Dev log: 2026-10-18

## 1. Review of the docs and scaffold

Reviewed `docs/sentrix-architecture.md`, `docs/handoff.md` and the Go scaffold. `go build` and `go vet` passed. Problems found:

- Supabase's transaction pooler (PgBouncer) does not support prepared statements, which pgx uses by default.
- `pgxpool.New` connects lazily, so a bad `DATABASE_URL` was not noticed until the first message.
- MQTT used a clean session, so QoS 1 messages sent while Go was down were lost.
- No validation of MAC format, topic/payload MAC agreement, or missing `ts`.
- `OFFLINE` devices never return to `ACTIVE`, and nothing sets `OFFLINE`.
- Subscribe errors were ignored.
- Only `os.Interrupt` was handled, not `SIGTERM`.
- The architecture doc still described Prisma and client-side defaults, but the real schema uses SQL migrations with database defaults and `set_updated_at` triggers.

## 2. Code fixes

`cmd/api/main.go`
- Pool config uses `pgx.QueryExecModeSimpleProtocol`.
- `db.Ping` at startup.
- Shutdown on `SIGINT` and `SIGTERM`.

`internal/ingest/ingest.go`
- `SetCleanSession(false)` (persistent session).
- Each subscribe is waited on and its error logged per topic.
- MAC is uppercased and must match `^[0-9A-F]{12}$`.
- A single reading's payload MAC must equal the topic MAC. Batched readings (from the mesh root) are exempt.
- Readings with `ts <= 0` are dropped.

`OFFLINE` handling was deliberately left alone, because reactivating on telemetry would skip calibration for a device that went offline while `CALIBRATING`.

## 7. Simulator (`cmd/simulator`)

A fake ESP32 that publishes to `sentrix/telemetry/{mac}`. The daily pattern is low overnight, a plateau 07:00–18:00, half load on weekends, plus noise.

```bash
# 7 days of history (used to train the ML side)
go run ./cmd/simulator -backfill-days 7

# live readings, with a 15A spike every 20th reading
go run ./cmd/simulator -live -interval 5s -spike-every 20
```

Flags: `-broker`, `-user`, `-pass` (default from `MQTT_*` env vars, else local Mosquitto), `-mac`, `-backfill-days`, `-backfill-delay` (default 150ms), `-live`, `-interval`, `-spike-every`, `-spike-amps`, `-seed`.

### Things learned while testing it

- **Ingest speed:** the Go app ingests about 8–9 readings per second, because each reading costs several round trips to Supabase. Mosquitto keeps at most 1000 queued messages per client and drops the rest, so publishing faster loses data. A 20ms delay gave 1293 of 1440 rows. The default delay is 150ms, so a 7-day backfill takes about 25 minutes. Speeding up ingest (for example caching the device lookup) would help.
- **Duplicate app instances:** only one Go instance may use a client ID (`sentrix-go-backend`). `pkill -f cmd/api` does not kill the compiled binary of `go run`; use `pkill -f "go-build.*/api"`. Two copies kicked each other off the broker.
- **Stale persistent session:** after that, Mosquitto held a stale session and the Go app stopped receiving messages (no errors, subscribe looked fine). Reconnecting once with a clean session for the same client ID cleared it:
  ```bash
  mosquitto_sub -i sentrix-go-backend -t zz/none -W 1
  ```
  Whether the persistent session is worth keeping is an open question.
